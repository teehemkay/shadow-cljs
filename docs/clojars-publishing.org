#+TITLE: Publishing this fork to Clojars
#+OPTIONS: toc:2 num:nil

* Why this exists

This is a fork of upstream =thheller/shadow-cljs=. The upstream Clojars group =thheller= is owned by the original author and cannot be deployed to, so the fork publishes under a group we control: =org.clojars.teehemkay=. The =org.clojars.<username>= group is auto-verified for any registered Clojars account, so no DNS or domain setup is required.

* Coordinates and versioning

The artifact is =org.clojars.teehemkay/shadow-cljs=. Versions follow the scheme =<upstream-version>-bun=, which keeps the upstream base version visible while marking the artifact unambiguously as this fork (e.g. the first release was =3.3.7-bun=, cut from upstream =3.3.7=; the current release is =3.4.11-bun=, cut from upstream =3.4.11=). Released versions on Clojars are immutable: a published version can never be overwritten or deleted, so to re-release you bump the suffix.

Consumers depend on it like any Clojars artifact (Clojars is a default repository for both tools.deps and Leiningen):

#+begin_src clojure
;; deps.edn
org.clojars.teehemkay/shadow-cljs {:mvn/version "3.4.11-bun"}

;; Leiningen
[org.clojars.teehemkay/shadow-cljs "3.4.11-bun"]
#+end_src

* What the published jar contains

The jar is a full drop-in for upstream =thheller/shadow-cljs=. It carries the complete ClojureScript compiler and tooling — including the fork's =:js-runtime= feature — and the compiled =localhost:9630= dashboard UI (the shadow-grove SPA, the build-report UI, CSS, and image assets under =shadow/cljs/ui/dist= and =shadow/cljs/build_report/dist=). The dashboard is served straight from the jar's classpath (=shadow.cljs.devtools.server= mounts =classpath-handler "/shadow/cljs/ui/dist"=), so =shadow-cljs server= / =watch= bring up the running dashboard exactly as upstream does.

The compiled dashboard assets are committed to the repo (=src/ui-release/shadow/cljs/ui/dist/js/{main,code-editor}.js=, =ui/dist/css/ui.css=, and =build_report/dist/js/{main.js,manifest.edn}=), so a plain =lein install= from a clean checkout produces the full-drop-in jar — no UI rebuild or =shadow-grove= checkout required. Only the source maps (=*.js.map=) stay gitignored (debug-only, ~6.3MB, regenerated every build; the dashboard renders without them). These committed assets are a point-in-time snapshot of the dashboard build; rebuild and re-commit them (see [[*Building the dashboard UI]]) only when syncing to a new upstream version, which changes the dashboard source.

* Deploy configuration

=project.clj= declares a =:deploy-repositories= entry that reads credentials from the environment, so the deploy token never lands in the repository:

#+begin_src clojure
:deploy-repositories
[["clojars" {:url "https://clojars.org/repo"
             :username :env/clojars_username
             :password :env/clojars_password
             :sign-releases false}]]
#+end_src

=:sign-releases false= because Clojars no longer requires GPG signatures. Leiningen resolves =:env/clojars_username= to the =CLOJARS_USERNAME= environment variable and =:env/clojars_password= to =CLOJARS_PASSWORD=.

* The deploy token

Clojars no longer accepts the account password for deploys — a scoped deploy token is required. Create one at https://clojars.org under Dashboard → Deploy Tokens (scope it to =org.clojars.teehemkay/shadow-cljs=). The token is stored in 1Password at =op://devops/clojars-deploy-token/credential= and is read at deploy time via the =op= CLI, so it is never written to the repo, =project.clj=, or shell history. The token must belong to the =teehemkay= account, since the group is created/verified from the deploying account on first push.

Note: with 1Password desktop-app integration, =op read= works (prompting via Touch ID) even when =op whoami= reports "account is not signed in".

* Syncing to a new upstream version

Upstream =thheller/shadow-cljs= ships frequently; this fork periodically catches up and re-cuts. The =:js-runtime= feature is small and well-isolated, so the merge is usually cheap — historically a single conflict, in =project.clj=. (The 3.3.7 → 3.4.11 sync absorbed 49 upstream commits — including the =shadow/util= → =shadow/fswatch= rewrite and the =shadow-undertow= → =shadow-http= server swap — with =project.clj= as the only conflict.)

1. Remotes. =origin= is the fork (=teehemkay/shadow-cljs=); =upstream= is =thheller/shadow-cljs=. Add upstream once if missing, then fetch:

   #+begin_src sh
   git remote get-url upstream || git remote add upstream https://github.com/thheller/shadow-cljs.git
   git fetch upstream --tags
   #+end_src

2. Size the gap. The target version is upstream's latest =bump <x.y.z>= commit:

   #+begin_src sh
   git log upstream/master --oneline | grep -m1 'bump '   # latest upstream version
   git rev-list --count master..upstream/master           # commits to absorb
   #+end_src

3. Branch and merge, so =master= stays clean until the merge is validated:

   #+begin_src sh
   git checkout -b sync/upstream-<x.y.z>
   git merge upstream/master
   #+end_src

   Tip: =git merge --no-commit --no-ff upstream/master= previews the conflict surface without creating the commit — inspect =git status= / =git diff=, then either resolve or =git merge --abort= if the scope is bigger than expected.

4. Resolve =project.clj= — the one expected conflict. The =:dependencies= block auto-merges to upstream's bumped versions; typically only the =defproject= line conflicts. Keep the fork's side for what the fork owns — the coordinate =org.clojars.teehemkay/shadow-cljs=, the =:url=, and the =:repositories= / =:deploy-repositories= blocks — and take upstream's side for everything else (dependency versions, profiles). Set the version to =<x.y.z>-bun=. Then confirm nothing else lingers anywhere: =git grep -nE '^(<<<<<<<|>>>>>>>)'=.

5. Validate before committing. The fork's tests run alongside the full upstream suite:

   #+begin_src sh
   lein javac    # compiles upstream's Java (e.g. the fswatch sources)
   lein test     # expect the js-runtime / cli-opts tests green among the rest
   #+end_src

6. Commit the merge, recording in the message what conflicted and how it was resolved — future syncs read it.

7. Continue. A new upstream base means the dashboard source changed, so rebuild it (see [[*Building the dashboard UI]]), then publish (see [[*Releasing a new version]]). Verifying against the downstream consumers (=kiln=, =bunbushka=, =ik=) before publishing is cheap insurance: =lein install= the synced version locally, point each consumer's =deps.edn= at =<x.y.z>-bun=, and run its build/tests.

* Releasing a new version

Picks up from a completed sync (branch merged, version-bumped, tests green) — or stands alone for a re-release of the same upstream base.

1. Set the version string in =project.clj= to =<upstream-version>-bun= (already done during a fresh sync; for a same-base re-release, bump the =-bun= suffix instead — published versions are immutable).
2. If this sync brought a new upstream version (the dashboard source changed), rebuild the dashboard UI into =src/ui-release= (see [[*Building the dashboard UI]]) and commit the refreshed assets. For a re-release of the same upstream base, the committed assets already make the jar a full drop-in — skip to validation.
3. Validate the build locally first — this is reversible, the deploy is not. Confirm the jar carries the dashboard:

   #+begin_src sh
   lein install
   unzip -l ~/.m2/repository/org/clojars/teehemkay/shadow-cljs/<version>/shadow-cljs-<version>.jar | grep ui/dist/js/main.js
   #+end_src

4. Deploy, sourcing the token straight from 1Password into the environment for the single command:

   #+begin_src sh
   CLOJARS_USERNAME=teehemkay \
   CLOJARS_PASSWORD="$(op read 'op://devops/clojars-deploy-token/credential')" \
   lein deploy clojars
   #+end_src

5. Verify the artifact is live:

   #+begin_src sh
   curl -s "https://clojars.org/api/artifacts/org.clojars.teehemkay/shadow-cljs" \
     -H "Accept: application/json"
   #+end_src

   A successful first deploy of a brand-new artifact prints a harmless "Could not find metadata ... maven-metadata.xml" line before sending the freshly created metadata — there is no prior metadata to merge.

* Building the dashboard UI

Producing the full-drop-in jar (one that ships the =localhost:9630= UI) reconstructs the maintainer's dev environment. The key subtlety: the dashboard is built from the shadow-grove *source*, not the =com.thheller/shadow-grove= jar pinned in the =:cljs= profile. That pin (=0.5.0=) is stale even upstream — the current dashboard source requires newer grove namespaces (e.g. =shadow.grove.kv=) that exist only on grove =master=, so building against the 0.5.0 jar fails with "namespace shadow.grove.kv is not available".

1. Sibling shadow-grove checkout. Clone =thheller/shadow-grove= as a sibling =../shadow-grove= and check out =master=. grove stopped bumping its version at =1.0.4= (2025-04) but kept developing on =master=; its =master= tip is the commit contemporaneous with the synced shadow-cljs version. =src/dev/build.clj= (=build/css-release=) indexes =../shadow-grove/src/main= for shadow-css class definitions, and the JS build needs grove =master= on its classpath.

2. UI npm deps. =cd packages/ui && npm install= (codemirror, react 16, xterm, etc.).

3. Put grove =master= source on the =:cljs= classpath. *Temporarily* edit the =:cljs= profile in =project.clj=: comment out =[com.thheller/shadow-grove "0.5.0"]= and add =:source-paths ["../shadow-grove/src/main"]=. This is temporary because committing it would make every =+cljs= build (incl. CI) depend on the sibling checkout — revert it once the assets are written. (=lein install=/=deploy= does not activate =:cljs=, so the revert does not affect the jar, which reads the already-built assets from =src/ui-release=.)

4. CSS build → writes =src/ui-release/shadow/cljs/ui/dist/css/ui.css=:

   #+begin_src sh
   lein with-profiles +cljs run -m clojure.main -e "(require 'build)(build/css-release)"
   #+end_src

5. JS build → writes the optimized dashboard + build-report JS into =src/ui-release/=:

   #+begin_src sh
   lein with-profiles +cljs run -m shadow.cljs.devtools.cli release ui build-report
   #+end_src

6. Revert the temporary =project.clj= edit from step 3, then commit the refreshed assets so the jar stays reproducible from a bare checkout. They are gitignored, so force-add the functional files only (not the =*.js.map= source maps):

   #+begin_src sh
   git add -f src/ui-release/shadow/cljs/ui/dist/js/main.js \
              src/ui-release/shadow/cljs/ui/dist/js/code-editor.js \
              src/ui-release/shadow/cljs/ui/dist/css/ui.css \
              src/ui-release/shadow/cljs/build_report/dist/js/main.js \
              src/ui-release/shadow/cljs/build_report/dist/js/manifest.edn
   #+end_src

   The dashboard can be smoke-tested before deploy by booting any consumer against the local install and hitting the UI: =clojure -M:<cljs-alias> -m shadow.cljs.devtools.cli server= then =curl -s localhost:9630/css/ui.css=.
