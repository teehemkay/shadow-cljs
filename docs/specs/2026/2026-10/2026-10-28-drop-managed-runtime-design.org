* What this is

The fork of shadow-cljs (=org.clojars.teehemkay/shadow-cljs=) adds two things to upstream:
- a /selector/: the =:js-runtime= build key, the =--js-runtime= CLI flag, and the two places upstream hard-codes =node=, which are =:node-test= autorun and =node-repl='s process;
- a /managed runtime/: after each successful compile of a watched build carrying =:js-runtime=, the watch worker spawns =bun= on a small bootstrap script that requires =out/<build>.js= and keeps the process alive, keeps one such process running, and stops it with the worker. Since 3.5.7-bun.2, an eval that arrives before that process connects waits for it.

The managed runtime gives agents in kiln, ik and bunbushka one command, =bb dev=, after which =(shadow/repl :dev)= has a runtime to evaluate in. It costs most of the fork's diff against upstream ([[#fork-today]]), every October review round, the 3.5.7 sync's =worker.clj= conflict, [[id:20261018T195432.672778][two known limitations]], and [[id:20261021T185802.026641][the first-compile bug]]. The survey is [[id:20261024T174047.298693][the IDEA this spec settles]].

This spec moves the launching out of the JVM. The fork keeps the selector and drops the managed runtime. A bb namespace in bunbushka starts the watch, starts Bun after the watch's first successful compile, interleaves Bun's output into its own, restarts Bun when it dies, and stops it on exit. The consumers' =bb dev= calls it. Agents see no change in workflow: run =bb dev=, then =(shadow/repl :dev)=.

* Scope and boundaries

In scope:
- the fork: removing the managed runtime, its tests, its CI job and its documentation;
- bunbushka: the launcher, its tests, its own =bb dev=, and its project template;
- kiln and ik: =bb dev= and the fork version, switched in one commit each;
- the instructions agents follow: the consumers' =CLAUDE.md= and =AGENTS.md=, kiln's development guide and architecture reference, and agent-skills' =cljs-repl-development= skill.

Out of scope, as boundary calls:
- *Browser runtimes.* Safari and Firefox Developer Edition for pure-ClojureScript web apps, and whether shadow-cljs or Figwheel Main serves them, are a separate project. A browser build needs no fork, so that project does not depend on this one. The launcher only keeps "start a runtime" as one function, so opening a URL in a browser could later be a second kind of runtime.
- *Historical documents.* Plans, journals, progress archives, specs and transcripts that describe the managed runtime stay as written; they record what was true then.
- *The upstream 3.5.8 sync.* It touches no file this spec changes ([[#release-order]]).

* What the fork keeps and drops                                    :normative:

** The fork drops the managed runtime
:PROPERTIES:
:CUSTOM_ID: drop-managed-runtime
:KIND: decision
:EVIDENCE: ev-fork-footprint ev-runtime-sites
:END:

The fork removes everything [[#fork-today]] lists under the managed runtime: the code in =src/main=, the =src/repl= suite and its probes, its CI and publishing-doc entries, and its documentation. A watched build carrying =:js-runtime= then behaves as upstream's does: the watch compiles, and nothing starts a process.

The eval wait 3.5.7-bun.2 added goes with it, since it waits on the managed process. An eval with no connected runtime fails at once with upstream's "no available JS runtime", and callers wait for a runtime themselves ([[#callers-wait]]).

With the managed runtime gone, [[id:20261018T195432.672778][the two known limitations]] have nothing left to describe and close with this change.

** The fork keeps the selector
:PROPERTIES:
:CUSTOM_ID: keep-selector
:KIND: decision
:EVIDENCE: ev-runtime-sites
:END:

The selector stays as it is: the =:js-runtime= key and its spec, the =--js-runtime= flag, =:node-test= autorun through =shared/js-runtime-file-argv=, =node-repl= through =shared/js-runtime-stdin-argv=, the stdin import-path fix in =build/node.clj=, and the warning when =:js-runtime= is set on a build that ignores it. None of it starts a long-lived process: autorun waits for its test process to exit, and =node-repl= owns its process for the REPL's lifetime, as upstream's does with =node=.

** The worker output printer fix stays
:PROPERTIES:
:CUSTOM_ID: keep-printer-fix
:KIND: decision
:EVIDENCE: ev-fork-footprint ev-build-lines
:END:

The fork's change to the worker output printer in =shadow.cljs.devtools.server.util= stays. Upstream's printer buffers one message and drops it when the next one overtakes it, a build failure included. The fork's buffer holds 1024 and never queues verbose-only =:build-log= events. The launcher reads the printed compile lines ([[#reads-watch-output]]), so a dropped =Build completed.= line would leave Bun unstarted. The fix is upstream material on its own merits and is no part of the managed runtime.

* The launcher                                                     :normative:

** The launcher is a bb namespace in bunbushka
:PROPERTIES:
:CUSTOM_ID: launcher-home
:KIND: decision
:EVIDENCE: bare
:BARE-REASON: A placement choice between repositories; nothing executable distinguishes them.
:END:

The launcher is one bb namespace shipped in bunbushka, published as =com.exidia/bunbushka=, and each consumer's =bb.edn= pulls it in through =:deps=. bunbushka is already "ClojureScript on Bun" plus the project template every new project is scaffolded from, so the template gets the launcher in the same release. tmk accepted this on [2026-10-28 Wed]; the alternatives are [[#rejected-bd-subcommand]] and [[#rejected-copies]].

** The launcher learns about compiles from the watch's own output
:PROPERTIES:
:CUSTOM_ID: reads-watch-output
:KIND: decision
:EVIDENCE: ev-consumer-entry ev-build-lines
:END:

The launcher runs the consumer's watch command, =bun run --bun shadow-cljs watch <build>=, as its child, copies the child's stdout and stderr to its own stdout unchanged, and reads both line by line. Both, because a watch that starts its own server prints its compile lines on stderr: a stand-in reading only stdout never saw =[:dev] Build completed.= on [2026-10-28 Wed], and saw it once it read stderr too. A line starting =[:<build>] Build completed.= is a successful compile of the watched build; =[:<build>] Build failure:= is a failed one. These come from =shadow.cljs.devtools.server.util=, and it is the only coupling the launcher has to shadow. tmk accepted this on [2026-10-28 Wed]; the alternatives are [[#rejected-build-hook]] and [[#rejected-mtime]].

The coupling's failure is loud. If upstream rewords the line, Bun never starts: no =[bun]= line appears, and =(shadow/repl :dev)= reports no available JS runtime.

The launcher gives the watch a stdin pipe it holds open for its whole life. A watch that started its own server polls stdin and stops its builds once stdin closes:

Holding the pipe open is safe either way, so the launcher never depends on the answer, and its shutdown never relies on the poll.

** bb dev works beside a server that is already running
:PROPERTIES:
:CUSTOM_ID: attached-watch
:KIND: decision
:EVIDENCE: bare
:BARE-REASON: Observed in a throwaway project on [2026-10-28 Wed]; a block would start two shadow JVMs per audit.
:END:

When a shadow server is already running in the project, such as the one kiln's =bb watch= starts for its =:test= build, the launcher's =shadow-cljs watch <build>= attaches to it instead of starting another. The launcher handles that case exactly like the other, because the attached CLI prints the same lines. Observed on [2026-10-28 Wed] with the fork's 3.5.7-bun.2, a server watching =:test=, and a second CLI running =watch dev=:
- the attached CLI printed =shadow-cljs - connected to server=, then =[:dev] Build completed.= for the first compile and again for a recompile after an edit;
- a third CLI asking to watch =:dev= printed =already started= with a stack trace and exited 1;
- stopping the attached CLI stopped the =:dev= watch (its output stopped updating after a later edit), and the server and its =:test= watch kept running.

So =bb dev= and continuous testing run side by side, in either start order. tmk ruled on [2026-10-28 Wed] that refusing a running server would block that pairing ([[#rejected-refuse-server]]). A =:dev= already watched elsewhere needs no detection of its own: the watch exits 1, and the launcher reports it and exits ([[#stop-together]]).

** The build's :js-runtime chooses the program
:PROPERTIES:
:CUSTOM_ID: runtime-from-config
:KIND: decision
:EVIDENCE: ev-runtime-sites
:END:

The launcher reads the build's =:js-runtime= from =shadow-cljs.edn=: =:bun= runs =bun=, and =:node= or no key runs =node=. Once the managed runtime is gone, nothing in the fork reads the key on a =:node-script= build ([[#fork-today]]), so the launcher becomes its reader. The key keeps meaning what it says, and the =cljs-repl-development= skill, which reads it to tell which runtime a project uses, stays correct. Reading the file tolerates reader tags it does not know. This is this spec's call, explained to tmk on [2026-10-28 Wed].

** Bun starts after the watch's first successful compile
:PROPERTIES:
:CUSTOM_ID: start-after-compile
:KIND: guarantee
:EVIDENCE: ev-build-lines ev-client-signals ev-bun-refused
:END:

Bound: the launcher starts Bun only after the watch it started has printed =Build completed.= for the build it was given. It never starts Bun on an output file left by an earlier watch. Such a file would connect, be rejected as =Stale Output!=, and stop retrying for good ([[#launcher-ground]]).

Trust boundary: the line means the build's output is written. The printer prints it after the flush stage, in =shadow.cljs.devtools.server.util=. A Bun started then finds the server already listening, since the CLI's watch starts the server before its first compile. Were the server late, the client's own retry covers about 15 s, and it works under Bun ([[#launcher-ground]]). The launcher adds no readiness check of its own ([[#rejected-readiness-check]]).

** Bun's output is interleaved into bb dev's, prefixed
:PROPERTIES:
:CUSTOM_ID: interleaved-output
:KIND: decision
:EVIDENCE: ev-client-signals
:END:

Each line Bun writes to stdout or stderr goes to the launcher's stdout prefixed with =[bun]= and a space. There is no separate log file. Agents run =bb dev= in the background and read its output, so the client's own signals (=ready!=, =giving up=, =Stale Output!=), the =:main='s output and a crash's stack trace all reach the agent where it already looks. They replace the managed runtime's "never connected" diagnostic and its log file. tmk accepted this on [2026-10-28 Wed].

The launcher's own reports are prefixed with =[bb dev]= and a space, so its lines, shadow's and Bun's never read as each other's.

** A Bun that dies is restarted, unless it died at start
:PROPERTIES:
:CUSTOM_ID: restart-policy
:KIND: decision
:EVIDENCE: bare
:BARE-REASON: Behaviour to build; the launcher's own test suite is its evidence.
:END:

When Bun exits while the launcher runs, the launcher reports the exit code and how long Bun ran, then:
- if Bun ran 5 s or longer, it restarts Bun at once;
- if Bun ran under 5 s, it waits for the next =Build completed.= line and starts Bun then.

A Bun that dies at start almost always died loading the build's code, so restarting at once would load the same code and loop. The agent's next edit fixes it, and its compile is the retry. This mirrors the managed runtime, whose next compile started a fresh process. tmk ruled "restart it and report it" and accepted the fast-death rule on [2026-10-28 Wed]. The 5 s threshold is this spec's call.

The report is one line, such as =[bb dev] bun exited with code 1 after 0.4s; waiting for the next successful compile=. The lines Bun printed before dying are already above it ([[#interleaved-output]]).

** Each child runs under a guard that outlives the launcher
:PROPERTIES:
:CUSTOM_ID: guard-children
:KIND: decision
:EVIDENCE: bare
:BARE-REASON: Observed in a throwaway project on [2026-10-28 Wed] and [2026-10-29 Thu]; a block would start a shadow JVM per audit and SIGKILL a process.
:END:

The launcher starts the watch and Bun each through one small guard script that bunbushka ships beside the launcher, run as =bun <guard> <command…>=. The guard:
- starts the command in a process group of its own;
- checks once a second whether its parent process has changed, which means the launcher is gone;
- on that, or on SIGTERM or SIGINT, stops the group: SIGTERM to the whole group, then SIGKILL to it 2 s later;
- when the command exits by itself, stops the group the same way before exiting, since the command's own children may still be running;
- exits with the command's exit code, or non-zero when the guard started the stop, and only once the stop has finished: the group is empty, or the SIGKILL has gone out.

The last rule takes precedence over the command's exit. The watch is a chain, =bun run= starting node starting the JVM, and the first link can die on SIGTERM while the JVM is still stopping; a guard that exited with it would never send the SIGKILL. The launcher's tests cover this with a fake command whose child ignores SIGTERM.

The group matters for the watch: =bun run --bun shadow-cljs watch= starts node, which starts the JVM, and only signalling the group reaches all three. One script covers Bun and the watch, so Bun's command line stays plain. tmk chose guarding both on [2026-10-29 Thu]; the alternative was guarding Bun only and recording the watch orphan as a known limit.

Why it is needed, observed with a stand-in launcher in bb that started the watch, waited for its compile line, then started Bun, and was then SIGKILLed:
- with only a parent check preloaded into Bun, Bun exited within 1 s, and =bun run=, node and the JVM were all still running 40 s later. Today's =bb dev= orphans the watch the same way, since it runs the watch with =shell= and nothing else;
- with both children under a guard of this shape, on [2026-10-29 Thu], no process of the project was left 10 s after the SIGKILL, and the port its server held was free.

** Stopping bb dev stops Bun
:PROPERTIES:
:CUSTOM_ID: stop-together
:KIND: guarantee
:EVIDENCE: bare
:BARE-REASON: Behaviour to build; the launcher's own test suite is its evidence.
:END:

Bound: when the launcher exits on SIGINT or SIGTERM, or because its watch exited, it stops Bun and its watch before it exits: SIGTERM, then a forced kill after 2 s. A watch that exits on its own makes the launcher exit non-zero, reporting the watch's exit code. Stopping its watch stops only the build it watches: a server it attached to keeps running, with that server's other builds ([[#attached-watch]]).

A SIGKILL to the launcher alone is covered by the guards instead ([[#guard-children]]): Bun and the watch get SIGTERM within about 1 s, and SIGKILL 2 s after that.

Outside the bound: a SIGKILL that reaches the guards themselves, such as one sent to the launcher's whole process group. The guards die with the launcher, and the children, each in a group of its own, outlive them: Bun up and disconnected once the watch is gone ([[#run-output-directly]]), the watch running until something stops it. This follows from the guards' design and was not observed. It is upstream's position for any process started by hand.

* The consumers                                                    :normative:

** Callers wait for a runtime before their first eval
:PROPERTIES:
:CUSTOM_ID: callers-wait
:KIND: decision
:EVIDENCE: bare
:BARE-REASON: tmk's ruling on where waiting lives; the API it names is upstream's and unchanged.
:END:

Anything that evaluates ClojureScript right after =bb dev= starts waits for a runtime first. It polls =(shadow.cljs.devtools.api/repl-runtimes <build>)= in Clojure mode until the result is non-empty, then selects the build and evaluates. This is upstream's contract: a runtime is the caller's to wait for. tmk ruled this on [2026-10-28 Wed], after a side note pointed out that the 3.5.7-bun.2 wait goes with the managed runtime ([[#drop-managed-runtime]]). The alternatives are [[#rejected-fork-wait]] and [[#rejected-ready-line]].

The callers are:
- agents following the =cljs-repl-development= skill and the spike skill's =cljs-repl-mechanics.md=, whose setup steps gain the wait;
- agent-skills' ClojureScript session test, which found the first-compile bug.

** Each consumer bumps the fork and switches bb dev in one commit
:PROPERTIES:
:CUSTOM_ID: atomic-switch
:KIND: decision
:EVIDENCE: ev-consumer-entry
:END:

kiln, ik and bunbushka each change the fork version and their =bb dev= task in the same commit. Either half alone breaks =bb dev=: the old fork with the launcher starts two Bun processes for one build, and the new fork with the old task starts none.

bunbushka's template changes in the same bunbushka release that ships the launcher, so a project scaffolded from it gets a matching pair.

** The instructions agents follow say bb dev starts Bun
:PROPERTIES:
:CUSTOM_ID: docs-rewritten
:KIND: decision
:EVIDENCE: ev-managed-mentions
:END:

Every instruction surface that says =(shadow/repl …)= launches a managed Bun process is rewritten to say that =bb dev= starts Bun once the first compile completes, and that the first eval waits for a runtime ([[#callers-wait]]). The rule "do not run =bun out/dev.js= yourself" stays, with its reason changed: =bb dev= owns that process. The surfaces, at each repository's =main= on [2026-10-28 Wed]:

** Release order
:PROPERTIES:
:CUSTOM_ID: release-order
:KIND: decision
:EVIDENCE: bare
:BARE-REASON: An ordering argument over releases; nothing executable distinguishes the orders.
:END:

1. The fork releases without the managed runtime.
2. bunbushka releases the launcher and its template, built against that fork release.

* Rejected alternatives                                            :normative:

** Rejected: agents start Bun themselves
:PROPERTIES:
:CUSTOM_ID: rejected-agent-starts-bun
:KIND: rejection
:EVIDENCE: ev-client-signals
:END:

Upstream's model: =bb dev= starts only the watch, and the agent runs =bun out/dev.js= as a second step. It needs no code, but an agent would have to sequence two background processes and wait for the first compile with no clean signal. Starting early on a stale =out/dev.js= gets the output rejected, and the client then stops retrying for good. An agent that forgets to stop Bun just moves the orphans from the fork to the agent. tmk ruled on [2026-10-28 Wed] that =bb dev= keeps starting Bun for agents. Starting Bun by hand stays possible for tmk.

** Rejected: a shadow build hook signals the launcher
:PROPERTIES:
:CUSTOM_ID: rejected-build-hook
:KIND: rejection
:EVIDENCE: bare
:BARE-REASON: An architectural choice; the hook would run in the JVM this spec empties of runtime code.
:END:

A =:build-hooks= function at the =:flush= stage could write a marker file the launcher watches. That's a real API rather than log text, but the hook runs inside shadow's JVM, so its code would ship on shadow's classpath, in the fork or in bunbushka's jar. That puts code back where this spec removes it, and adds a file protocol between two processes.

** Rejected: watch the output file's modification time
:PROPERTIES:
:CUSTOM_ID: rejected-mtime
:KIND: rejection
:EVIDENCE: bare
:BARE-REASON: The defect is a missing signal, which no block can show present.
:END:

Polling =out/dev.js='s modification time needs no parsing, but it cannot tell a failed compile from a good one, and it can fire while the file is still being written.

** Rejected: the launcher as a bd subcommand
:PROPERTIES:
:CUSTOM_ID: rejected-bd-subcommand
:KIND: rejection
:EVIDENCE: bare
:BARE-REASON: A placement choice between repositories; nothing executable distinguishes them.
:END:

It would work for tmk's own projects, but every project would then need =bd= installed, and a project scaffolded from bunbushka's template would not run anywhere else.

** Rejected: a copy of the launcher in each repository
:PROPERTIES:
:CUSTOM_ID: rejected-copies
:KIND: rejection
:EVIDENCE: ev-consumer-entry
:END:

Four copies today (kiln, ik, bunbushka, the template) and one more per scaffolded project, drifting apart from the first fix onward.

** Rejected: drop the guarded websocket handler too
:PROPERTIES:
:CUSTOM_ID: rejected-drop-handler
:KIND: rejection
:EVIDENCE: ev-guarded-handler-reason
:END:

The brainstorm proposed dropping it, gated on upstream's handler coping once Bun is started from outside. The commit that added it says upstream's handler throws whenever a peer dies mid-send, and the launcher's restarts make such peers. The gate fails on that account alone ([[#keep-guarded-handler]]).

** Rejected: keep a small eval wait in the fork
:PROPERTIES:
:CUSTOM_ID: rejected-fork-wait
:KIND: rejection
:EVIDENCE: bare
:BARE-REASON: tmk's ruling on where waiting lives.
:END:

An eval with no runtime could wait up to a bound for one to connect, as 3.5.7-bun.2's does. Callers would not change, but the wait sits in the worker and REPL files, the conflict surface this spec exists to clear.

** Rejected: bb dev announces readiness
:PROPERTIES:
:CUSTOM_ID: rejected-ready-line
:KIND: rejection
:EVIDENCE: bare
:BARE-REASON: tmk's ruling on where waiting lives.
:END:

The launcher could print a line once Bun's client prints =ready!=, for callers to wait on. Only something reading =bb dev='s output sees it; a caller that only talks nREPL does not. The client's own =ready!= line reaches =bb dev='s output anyway ([[#interleaved-output]]).

** Rejected: refuse to start beside a running server
:PROPERTIES:
:CUSTOM_ID: rejected-refuse-server
:KIND: rejection
:EVIDENCE: bare
:BARE-REASON: tmk's ruling; the attached case's behaviour is recorded in attached-watch.
:END:

=bb dev= could exit when =.shadow-cljs/server.pid= shows a server running. It was proposed before the attached case was checked. tmk ruled it out on [2026-10-28 Wed]: it would rule out the REPL and continuous testing side by side, and the attached case turned out to need nothing special ([[#attached-watch]]).

** Rejected: a readiness check before starting Bun
:PROPERTIES:
:CUSTOM_ID: rejected-readiness-check
:KIND: rejection
:EVIDENCE: ev-client-signals ev-bun-refused
:END:

Polling the server's port before starting Bun adds nothing. The server is up before the first =Build completed.= line, and the client retries a refused connection for about 15 s under Bun as under Node.

* Left to the builder

- How the launcher finds the guard script, which ships in bunbushka's jar but must run as a file under =bun= ([[#guard-children]]).
- How bb consumes bunbushka: a Maven dependency pulls the jar's own dependencies onto bb's classpath. Check what that costs, and use a =:deps/root= or a separate artifact if it is heavy.
- The launcher's tests: a fake watch that prints the compile lines on cue and a fake runtime script that exits on cue cover [[#start-after-compile]], [[#restart-policy]] and [[#stop-together]] without shadow or Bun.
- Sorting =src/repl/shadow/cljs/js_runtime_test.clj= and =server_test_runner.clj= into what tests the selector, which stays, and what tests the managed runtime, which goes. The bootstrap's tests go, since the launcher runs the output directly ([[#run-output-directly]]).
- Rewriting each surface [[#docs-rewritten]] lists, and the fork's =doc/js-runtime.md= and =doc/js-runtime-architecture.md=.
