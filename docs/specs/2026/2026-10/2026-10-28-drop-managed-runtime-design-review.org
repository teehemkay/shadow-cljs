** Finding 1 — [P1] Keep guards alive until descendant cleanup finishes
:PROPERTIES:
:CUSTOM_ID: r1-f1
:CONFIDENCE: 0.98
:RAW_FILE: docs/specs/2026/2026-10/2026-10-28-drop-managed-runtime-design.org
:RAW_LINES: 414-418
:LOCATION: [[orgit-blob:~/dev/my/shadow-cljs::aa24ed3b08688f34a9176e6edcc8066ab32fbede/docs/specs/2026/2026-10/2026-10-28-drop-managed-runtime-design.org#414-418]]
:END:
#+begin_example
The guard must send SIGKILL after two seconds, but must also exit when its immediate command exits. If that command exits on SIGTERM while a descendant ignores it, immediate guard exit prevents escalation and leaves the descendant running. Ordinary command exit with surviving descendants is also undefined. This undermines the whole-process-group shutdown guarantee.
#+end_example

#+begin_example
Define cleanup precedence over immediate-child exit, including spontaneous exits. Require a probe where the immediate child exits but a descendant survives SIGTERM.
#+end_example

*Digest.*
- Frame: the guard decision ([[my:shadow-cljs/docs/specs/2026/2026-10/2026-10-28-drop-managed-runtime-design.org::#guard-children]]) lists what the guard does: own process group, parent check each second, SIGTERM to the group then SIGKILL 2 s later, and exit with the command's code when the command exits.
- Concern: the watch is a chain, =bun run= then node then the JVM. If =bun run= dies on SIGTERM first, the last rule makes the guard exit at once, before its 2 s SIGKILL, so a JVM slow to stop is left behind. The same holds when =bun run= exits on its own and leaves children running.
- Position: material and new. The spike passed because the JVM honoured SIGTERM, so it never exercised the gap. The approach holds; one rule is in the wrong order.
- Options: (a, lean) reword the rules: once stopping starts, the guard stays until its group is empty or the SIGKILL has gone out; when the command exits by itself, the guard signals what is left in its group the same way before exiting with the command's code. The launcher's tests cover it with a fake child that ignores SIGTERM. (b) Also add the reviewer's probe as an evidence block, which ties to finding 4.
- Question: reword the guard's rules as in (a)?

** Finding 2 — [P2] Define shutdown when bb dev owns the shared server
:PROPERTIES:

:END:
#+begin_example
The document promises coexistence in either start order, but records only the case where continuous testing starts the server first. In the reverse order, the JVM belongs to bb dev's guarded process group. The specified group shutdown therefore also terminates the server hosting the later test watch. The statement that stopping its watch stops only its build needs an ownership qualification.
#+end_example

#+begin_example
Specify the intended reverse-order shutdown behavior and its boundary, then record evidence for both start orders.
#+end_example

*Digest.*
- Frame: the attached-watch decision ([[my:shadow-cljs/docs/specs/2026/2026-10/2026-10-28-drop-managed-runtime-design.org::#attached-watch]]) says =bb dev= and continuous testing run side by side "in either start order", and the stop guarantee ([[my:shadow-cljs/docs/specs/2026/2026-10/2026-10-28-drop-managed-runtime-design.org::#stop-together]]) says stopping the launcher's watch stops only its own build.
- Concern: only one order was observed, testing first. When =bb dev= starts first, its watch owns the server JVM, and the test watch attaches to it. Stopping =bb dev= then kills that JVM, and continuous testing loses its server.
- Position: material and new, and correct as stated. It is not a regression: today's =bb dev= owns the server the same way. "Either start order" over-claims for shutdown.
- Options: (a, lean, subtractive) qualify both rows: whichever command started the server owns it, and stopping that command stops the other's builds too, as upstream shadow does today; record the owning case as observed. (b) Make the launcher refuse to own the server, for example by starting a separate =shadow-cljs server= first. That adds a process and a mode for a case nobody has hit.
- Question: qualify the two rows with the ownership rule, as in (a)?

#+begin_example
Several blocks pipe Git through grep and sed under set -e. A missing checkout or pinned commit can make Git fail while the final sed succeeds, so the block returns success with missing evidence. This particularly affects another machine without all four repositories at the hard-coded paths.
#+end_example

#+begin_example
Check repository and commit prerequisites explicitly and propagate failures from every pipeline stage using a declared compatible shell or separately checked commands.
#+end_example

*Digest.*
- Frame: the evidence blocks read pinned commits of the fork and its consumers with =git show= or =git grep=, piped through =grep= or =sed=, under =set -e=.
- Concern: =set -e= checks only a pipeline's last command. A missing repository or commit makes =git= fail, =sed= still succeeds, and the block "passes" with its evidence missing.
- Position: material and new, and true of every piped block. The audit would still show drift, since the output changes, but as missing lines rather than as a failure that names the cause.
- Options: (a, lean) add =set -o pipefail= as each piped block's second line. zsh and bash both accept it, and the mandated first line stays =set -e=. Re-run each block and get a green audit. (b) Explicit precondition checks per repository, which take more lines and give the same result.
- Question: add pipefail to every piped block, as in (a)?

*Action.* Fixed as (a), routed by tmk in bulk: =set -o pipefail= follows =set -e= in the nine blocks that pipe, every one but =ev-bun-refused=, found with an awk pass keyed on each block's =#+name:=. Before adding it, every piped =git grep= was checked to match at least once, so pipefail turns no legitimate empty result into a failure. Each of the nine was re-executed with the audit's recipe; every result came back byte-identical, and the audit is green. The reviewer's other route, explicit per-repository precondition checks, was not taken, since pipefail surfaces the same failures in one line.
