- *Symptom.* Since kiln moved to =3.5.7-bun= ([[orgit-rev:~/dev/my/kiln::8d4b7eb15e2d6caa270bc22e0d9e96704d0e12e0][8d4b7eb1]]) on [2026-10-19 Mon], every ClojureScript block that =bd org spike-verify= runs against a copy of kiln gets "No available JS runtime". kiln's own interactive sessions were unaffected.

The worker starts the managed process only after a compile, and =await-managed-runtime= returned at once when it found no process. [[orgit-rev:~/dev/my/shadow-cljs::3806490da122cf409c54081c5d994068af91f9aa][3806490d]] had removed the pre-compile wait of [[orgit-rev:~/dev/my/shadow-cljs::fd04ba4be06f61b1d84bbf2bed8067d7e75f28a3][fd04ba4b]]. An eval sent through one nREPL session during a cold first compile of kiln's =dev= build, as the verifier sends it: =3.4.11-bun= answered from Bun in 3 of 3 runs, =3.5.7-bun= failed 3 of 3, the fix answered 3 of 3. The npm launcher and =node_modules= were the same in every run, which clears kiln's pnpm reinstall.
- *Fix* on =wip/first-compile-wait=, [[orgit-rev:~/dev/my/shadow-cljs::c626dec23f5016ea5423a9e0a493c67ec2f11338][c626dec2]]: the eval waits up to 5 s for the first successful compile, then for the process as before. Every build without a runtime pays that wait during its first compile, since the state cannot yet say whether the build is managed. The =repl-tests= suites ran 35 tests and =lein test= 69, all green.

* IDEA Offer the guarded websocket handler to shadow-http upstream
:PROPERTIES:
:CREATED:  [2026-10-19 Mon 10:51]
:ID:       20261019T105108.243880
:END:

=shadow.cljs.devtools.server.web.websocket= is a deliberate copy of shadow-http's =CoreAsyncWebSocketHandler= that differs only in its write loop and how the loop's end closes the connection. Upstream taking both would fix every =ws-upgrade= caller and let the fork drop the copy.

Two limits of shadow-http itself, which the fork cannot reach through =WebSocketConnection=, belong in the same conversation:

- *A peer that never answers a server close keeps its socket.* =sendClose= only marks the exchange closed; the reader waits for the peer's reply with no timeout, and the interface has no way to drop the socket.
- *The reader answers a close it initiated.* =WebSocketExchange.process= calls =sendClose= on every close frame it reads, so the peer's reply to a server close gets a second close frame, which RFC 6455 section 5.5.1 does not ask for. Follows [[id:20261019T072556.442785][the guarded handler's remaining gaps]].
