** DONE A stopped runtime's websocket throws an uncaught SocketException
CLOSED: [2026-10-18 Sun 22:02]
:PROPERTIES:
:CREATED:  [2026-10-18 Sun 20:29]
:ID:       20261018T202955.497866
:END:

In two of three whole-namespace runs of =shadow.cljs.managed-runtime-test=, after =cljs-eval-evaluates-in-the-managed-runtime= and during =a-build-that-stops-being-managed-loses-its-process=, the log carried =Exception in thread "" java.net.SocketException: Socket closed= from =shadow.http.server.WebSocketExchange/sendFrame=, called from =CoreAsyncWebSocketHandler= on a virtual thread. The server writes a frame after the managed bun process's socket has closed. All tests passed every time; the trace is unasserted output and its root cause is unexamined.

A fourth run showed two other faces of the same send, at the same two points: =NullPointerException: Deflater has been closed= from =PerMessageDeflate.compress= under the same =sendText= call, and a =WARNING= =:shadow.remote.relay.local/client-not-keeping-up= for the just-disconnected runtime.

Root cause: shadow-http's =CoreAsyncWebSocketHandler= write loop sends whatever it took from =ws-out= with no guard, so a message in flight when the peer dies throws on the closing connection, uncaught on its virtual thread. The fork's managed runtime makes that common by killing a runtime while messages to it are in flight. Two paths do it:

- *Worker shutdown — fixed.* =do-shutdown= stopped the runtime before the worker left the relay, so the relay's worker-departure notice went to a dead runtime. The worker now leaves the relay first and waits for =connection-stop=; =the-worker-leaves-the-relay-before-its-runtime-stops= covers it.
- *A build that stops being managed — fixed.* =build-compile*= queues =:cljs-build-complete= for the runtimes, then =start-managed-runtime-after-build= kills the runtime at once, before the message clears shadow-http's async hops. A reorder cannot help, since the message precedes the kill.

The fork now upgrades its relay websockets through =shadow.cljs.devtools.server.web.websocket=, a deliberate copy of upstream's handler whose write loop ends quietly when a send fails because the peer left, told apart from a live-connection fault by waiting for =onClose=. That covers both paths and any other kill-while-sending. Three whole-namespace runs afterwards carried none of the traces. Proposing the guarded loop to shadow-http upstream would let the copy go.

** TODO The default watch output can drop a build-failure report
:PROPERTIES:
:CREATED:  [2026-10-18 Sun 20:37]
:ID:       20261018T203700.701114
:END:

=util/stdout-dump=, the printer =api/watch= uses when no =:log-chan= is given, reads through a one-slot sliding buffer, so a message arriving before its go-loop takes the previous one replaces it. [[id:20261018T195432.663061][The failed-compile test]] lost its =Build failure:= report that way whenever the worker's shutdown notice followed closely. A REPL user watching a build could lose a real failure report the same way. Upstream shadow-cljs behaviour; decide whether the fork should change it. Raised by a code review of =wip/managed-runtime-follow-ups=.
