** Two separate CSS pipelines — don't confuse them

There are two CSS configs and only one feeds the dashboard. =shadow-cljs.edn= has a top-level =:css= block emitting =ui/dist/main.css= (entries =shadow.cljs.ui.main= + =server.web=). =src/dev/build.clj='s =css-release= emits =ui/dist/css/ui.css= (entries =shadow.cljs.ui.main= + =code-editor=). The dashboard HTML (=server/web.clj=) links =/css/ui.css= → it's =build.clj='s output that matters, not the =shadow-cljs.edn= =:css= block. Indexing grove =master= (vs 0.5.0) grew =ui.css= 35.5 KB → 39.8 KB, a concrete signal the grove version mattered for styling, not just compilation.

** Committing past a directory-level global gitignore

The =src/ui-release= assets were ignored by a *global* =~/.gitignore= rule (=dist=, a bare dir name matching at any depth) plus project rules (=/src/ui-release/**/*.js=, nested =css/*.css=, =*.js.map=). You cannot re-include files under a parent dir that's excluded at directory level without first re-including the dir, and a deeper =.gitignore= (=css/*.css=) overrides root negations — fighting it with =!= negations across multiple files is fragile. =git add -f <files>= is the robust move: it force-adds the named paths past all ignore rules, and once tracked git keeps tracking them (ignore only affects *untracked* files), so future UI rebuilds surface as normal modifications.

* Technical Insights

** A version pin can be silently stale when the published artifact's main consumers never exercise it

=shadow-grove 0.5.0= is pinned in shadow-cljs's =:cljs= profile and that's what library consumers resolve — but library consumers never build the dashboard, so nobody notices the pin is ~5 years behind the source the dashboard actually needs. The pin "works" precisely because the thing it's wrong for (the UI build) is a maintainer-local step, not part of the published artifact's normal use. Lesson: when a dependency is only exercised by an out-of-band build step, its declared version drifts from reality unnoticed. Treat such pins as documentation, not truth, and verify against the source the build step actually consumes.

** Escalating verification for a "drop-in"/"stand-in" claim

"Is X a drop-in replacement?" deserves a verification ladder, not a single check: it compiles → its own tests pass → real downstream consumers build/test against it → the artifact serves/runs from its packaged form (not the dev tree) → it behaves correctly at runtime (render/exec) → the *published* copy is byte-checked → it's reproducible from a clean checkout. Each rung catches a failure class the previous can't. The "serve from the jar, not the working tree" and "build in a fresh worktree" rungs specifically catch packaging/classpath bugs that all dev-tree testing is blind to.
